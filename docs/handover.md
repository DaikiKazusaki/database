# 引き継ぎ

このサイトを次の代へ渡すための台帳．**担当者が替わったら必ずこのファイルを更新すること．**

いちばん大事なのは，どのサービスも**常に2人以上がオーナー権限を持っている**状態を保つこと．
1人が卒業・失踪しても運用が止まらないようにするのが目的で，これを守れていれば他は後から直せる．

> 個人名ではなく**役職名**で書くこと．個人名で書くと，その人の卒業と同時に窓口が消える．

## アカウント台帳

実際のパスワードはここに書かない．部のパスワードマネージャに入れ，ここには「どこにあるか」だけを書く．

| サービス | 用途 | オーナー | 課金 | 止まると何が起きるか |
| --- | --- | --- | --- | --- |
| GitHub | ソースコード・CI・バックアップ | （未記入） | 無料 | 変更できなくなる．コードのコピーは各自の手元に残る |
| Vercel | サイトのホスティング | （未記入） | （未記入） | サイトが見られなくなる |
| Neon | データベース | （未記入） | （未記入） | **棋譜が失われる．最も重い** |
| パスワードマネージャ | 上記の資格情報 | （未記入） | （未記入） | 各サービスに入れなくなる |

### 部のアカウントへの移管

**2026-08-29時点で，上記はすべて作者個人のアカウントに紐づいている．**
これが最大の継続性リスクなので，下記を実施すること．

1. 部で代々引き継ぐメールアドレス（Googleアカウント）を1つ用意する
2. GitHub Organization を作り，リポジトリを移管する（URLが変わっても旧URLからリダイレクトされる）
3. Vercel Team を作り，プロジェクトを移す．環境変数を移すのを忘れないこと
4. Neon Organization に移す．**移管前に必ず `npm run backup` を取っておく**
5. 各サービスに副オーナーをもう1人追加する
6. この台帳を埋め，`app/components/footer.tsx` の開発者クレジットを見直す

## シークレットの置き場所

| 場所 | 何を置くか |
| --- | --- |
| Vercel の環境変数 | `DATABASE_URL`・`BASIC_AUTH_USER`・`BASIC_AUTH_PASSWORD` |
| GitHub Actions secrets | `DATABASE_URL`（日次バックアップ用）．任意で `BACKUP_REPO`・`BACKUP_TOKEN` |
| 各自の手元 | `.env.local`（`.env.example` をコピーして作る．コミットしない） |

## Basic認証のパスワードを変えるとき

部員全員で1つのパスワードを共有しているため，卒業生も知り続ける．**年度替わりに必ず更新すること．**

1. 新しいパスワードを決め，パスワードマネージャを更新する
2. Vercel の環境変数 `BASIC_AUTH_PASSWORD` を書き換える
3. 再デプロイする（環境変数の変更だけでは反映されない）
4. 部員へ周知する

なお，いまの仕組みでは**誰が棋譜を編集・削除したかが記録されない**．
個人アカウントでのログインと操作履歴の記録は，保守レビューで「今学期」の課題としている．

## 毎年やること

代替わりのたびに，次を上から順に確認する．

- [ ] 各サービスのオーナーが2人以上いることを確認する．卒業する人を外し，新しい担当者を足す
- [ ] Basic認証のパスワードを更新する（上記の手順）
- [ ] バックアップから実際に復元してみる（`npm run restore -- <ファイル>`）．手順書どおりに動くか確かめる
- [ ] 依存を一括更新し，CIが通ることを確認する
- [ ] この台帳の役職名・連絡先を，その年の体制に合わせて直す

## 掲載と削除の方針

**未策定．** このサイトには他大学の学生を含む実名・大学・学年が入っている．
卒業生から削除を求められたときに誰がどう対応するかを決めて，ここに書くこと．
最低限，次の3点があれば足りる．

- 誰の同意で載せているのか
- 削除依頼の連絡先（役職名で）
- 対応の手順（`UPDATE games SET deleted_at = now() WHERE id = ...;`）
